# AI Agent 工程流程

本文定义 AI agent 每次接任务时如何工作，避免只凭聊天上下文开发。

## 任务开始

每次新对话或上下文恢复，先读取 [project-status.md](project-status.md)，再判断任务类型：

- 需求澄清：读取产品设计和相关工程文档，输出事实、推测、问题。
- 产品规格：读取端到端实施流程和产品源文档，产出 PRD、用户旅程或验收标准。
- 交互/UI：读取端到端实施流程和功能切片，产出页面清单、用户流程、UI 规范或页面规格。
- 架构或计划：读取 `architecture.md`、`domain-model.md`、`implementation-roadmap.md`。
- 功能开发：读取对应功能切片、领域规则和质量门禁。
- 测试验收：读取 `quality-gates.md` 和验收标准，产出测试报告或问题清单。
- 发布交付：读取 `delivery-lifecycle.md` 和发布检查清单，产出发布说明或构建说明。
- 修 bug：先复现或定位，再修改。
- 代码评审：优先输出风险、缺陷和缺失测试。

## 上下文读取

推荐顺序：

1. `AGENTS.md`
2. `docs/engineering/project-status.md`
3. `docs/engineering/agent-startup.md`
4. 当前任务直接提到的文件
5. `docs/engineering/README.md`
6. 与任务相关的一到两份工程文档
7. 现有代码中相关目录

禁止为了“更完整”一次性读取所有文档和所有代码。

## 计划模板

非平凡任务先形成短计划：

```text
目标：
当前阶段：
当前切片：
范围内：
范围外：
涉及文件：
产物：
实现步骤：
验证方式：
风险或待确认：
```

计划不需要冗长，但要能指导实现。

## 开发策略

- 优先做垂直切片，让用户可以实际操作。
- 先复用已有模式，再新增抽象。
- 页面组件不写复杂业务判断。
- 领域规则写到 service，并配单元测试。
- 数据访问写到 Repository 和 DAO。
- 多表写入使用事务。
- 不为了未来功能引入过度设计。

## 文件修改规则

- 修改前先阅读相关文件。
- 不改无关文件。
- 不删除用户已有改动。
- 不把临时代码、注释掉的废弃代码、绕过类型检查的代码留在仓库。
- 代码结构变化必须同步更新工程文档。

## Drift 和代码生成流程

涉及 Drift 表、DAO、Riverpod 生成代码时：

1. 修改源文件。
2. 运行代码生成。
3. 运行 format。
4. 运行 analyze。
5. 运行相关测试。

推荐命令：

```bash
dart run build_runner build --delete-conflicting-outputs
dart format .
flutter analyze
flutter test
```

如果项目尚未初始化或命令不可用，交付时说明原因。

## 测试选择

- 纯领域规则：单元测试。
- Drift 查询和迁移：repository 或 DAO 测试。
- 表单和页面状态：widget 测试。
- 首页到记录上课闭环：集成测试或手工验收记录。
- 备份恢复：必须有自动化测试或详细手工脚本。

## 提交前自检

交付前检查：

- 是否满足本次任务目标。
- 是否处于正确生命周期阶段，是否跳过了必要的需求、UI 或验收产物。
- 是否破坏第一版不可破坏规则。
- 是否有新增业务规则未写入文档。
- 是否更新了 `project-status.md`。
- 是否运行了匹配的验证命令。
- 是否还有无法验证的风险。

## 交付模板

最终回复建议包含：

```text
已完成：
验证：
未完成或风险：
下一步建议：
```

内容要短而具体。不要把全部实现细节重复一遍。

## 何时询问用户

只有在以下情况才中断询问：

- 需求存在互斥解释，且本地文档无法判断。
- 继续实现可能导致明显返工。
- 涉及删除数据、改变第一版范围或更换技术栈。
- 需要用户提供真实设备、账号、证书或隐私数据。

其他情况下做保守合理假设，并在交付中标注。

## 常见反模式

- 只建数据库表，不做用户可操作闭环。
- 未定义需求和 UI 产物就直接进入开发。
- 每次新对话只靠聊天记忆，不读取 `project-status.md`。
- 把余额存成可手工改的单个数字。
- 在 UI 中硬编码课包选择算法。
- 用浮点数保存金额或课时。
- 把附件放到公共相册或公共下载目录。
- 忽略备份恢复，等最后再补。
- 把寒暑假自动排课提前做成第一版阻塞项。
