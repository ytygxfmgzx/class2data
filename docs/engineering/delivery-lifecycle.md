# 端到端实施流程

本文定义从需求设计到发布的完整工程流程。它补足“开发和测试之前”的产品、交互、UI、验收和发布环节。

## 总流程

```mermaid
flowchart LR
    A["需求输入"] --> B["需求设计"]
    B --> C["产品规格"]
    C --> D["信息架构与交互流程"]
    D --> E["UI 设计"]
    E --> F["技术设计"]
    F --> G["开发实现"]
    G --> H["测试验收"]
    H --> I["发布交付"]
    I --> J["复盘与下一轮"]
```

每个阶段都必须有明确产物和通过标准。未通过当前阶段门禁时，不进入下一阶段。

## P0：需求输入

目标：把用户的真实问题收集成可分析材料。

输入：

- 用户故事。
- 现有产品方案。
- 用户补充说明、约束、偏好。

产物：

- 原始问题记录。
- 需求来源索引。
- 待确认问题清单。

本项目已有产物：

- [../story.md](../story.md)
- [../interest-class-app-design.md](../interest-class-app-design.md)

通过标准：

- 能说清楚目标用户是谁。
- 能说清楚要解决的核心问题。
- 能区分第一版范围和后续版本范围。

## P1：需求设计

目标：把原始想法整理成稳定的产品需求。

产物：

- 产品定位。
- 第一版范围和非范围。
- 核心概念。
- 主要用户旅程。
- 业务规则和边界。
- 成功指标。
- 风险和待确认问题。

通过标准：

- 每个第一版功能都有明确用户价值。
- 核心对象和业务规则无明显冲突。
- 后续版本想法不会挤占第一版主线。
- 需求能映射到功能切片。

AI agent 检查方式：

- 对照 [feature-slices.md](feature-slices.md)，确认每个 Slice 都能追溯到需求。
- 对照 [domain-model.md](domain-model.md)，确认业务规则可实现。

## P2：产品规格

目标：把需求转成开发和验收都能使用的规格。

产物建议放置：

```text
docs/product/
  prd.md
  user-journeys.md
  acceptance-criteria.md
  glossary.md
  open-questions.md
```

必须包含：

- 用户角色和使用场景。
- 功能列表。
- 用户故事。
- 每个功能的验收标准。
- 字段和状态说明。
- 空状态、错误状态、边界状态。
- 不做什么。

通过标准：

- 开发 agent 不需要猜页面要做什么。
- 测试 agent 能直接从验收标准写测试用例。
- 用户能阅读并确认第一版是否符合预期。

## P3：信息架构与交互流程

目标：先确定用户如何完成任务，再讨论视觉样式。

产物建议放置：

```text
docs/design/
  information-architecture.md
  user-flows.md
  screen-inventory.md
```

必须包含：

- 导航结构。
- 页面清单。
- 主路径流程。
- 关键表单步骤。
- 页面间跳转关系。
- 快速记录路径。
- 异常路径，例如没有课包、课包过期、附件失败、备份恢复失败。

通过标准：

- 用户可以从首页完成最常用的记录上课动作。
- 日常记录路径不超过 10 秒的产品原则有交互支撑。
- 每个页面都有明确入口和返回路径。
- 没有为了展示档案而牺牲日常操作效率。

## P4：UI 设计

目标：定义可实现、可验收的移动端界面设计。UI 阶段的核心产物不是 Markdown，也不依赖 Figma；本项目默认交付高保真、可交互、本地可打开的 HTML 原型，用户确认样式和流程后再进入 Flutter 开发。

产物建议放置：

```text
docs/design/
  ui-guidelines.md
  visual-system.md
  prototypes/
    html/
      index.html
      styles.css
      app.js
      assets/
  screen-specs/
    home.md
    course-detail.md
    record-class.md
    package-form.md
```

必须包含：

- 设计原则。
- 色彩、字体、间距、圆角、图标、状态样式。
- 高保真可交互 HTML 原型。
- 组件清单。
- 表单控件规范。
- 空状态、加载态、错误态。
- 移动端适配规则。
- 关键页面的 HTML 原型入口。
- 开发完成后的页面截图，用于 UI 还原验收。

通过标准：

- 首页、记录上课、课程详情、课包续费、备份恢复这些关键页面包含在 HTML 原型中。
- HTML 原型可本地打开，可在移动端视口下预览。
- HTML 原型包含页面跳转、底部导航、关键弹层、表单状态和主要异常状态。
- 用户已确认 HTML 原型的整体样式、信息密度和主路径体验。
- 组件和状态覆盖完整，不只画理想状态。
- UI 文案短且贴近日常家长语言。
- 开发 agent 能按设计实现，而不是现场发挥。

## P5：技术设计

目标：把产品和 UI 设计映射成工程方案。

产物：

- [architecture.md](architecture.md)
- [domain-model.md](domain-model.md)
- [feature-slices.md](feature-slices.md)
- [implementation-roadmap.md](implementation-roadmap.md)

通过标准：

- 数据模型支撑需求和 UI。
- 关键业务规则有明确服务归属。
- 目录结构和状态管理方式明确。
- 测试策略覆盖高风险规则。

## P6：开发实现

目标：按垂直切片交付可运行能力。

产物：

- 可运行代码。
- 数据库迁移。
- 自动化测试。
- 必要的实现说明。
- 更新后的项目状态。

通过标准：

- 本切片用户路径可操作。
- 质量门禁通过。
- 没有破坏已完成切片。
- 文档和实现一致。

## P7：测试验收

目标：验证实现是否符合产品、UI、业务和技术标准。

测试维度：

- 需求验收：功能是否满足验收标准。
- 交互验收：主路径是否顺畅。
- UI 验收：页面是否符合设计规格。
- 业务验收：课包、销课、余额、附件、备份是否正确。
- 技术验收：分析、测试、迁移、性能是否达标。

产物建议放置：

```text
docs/qa/
  test-plan.md
  acceptance-report.md
  manual-test-scripts.md
  release-checklist.md
```

通过标准：

- 主路径验收完成。
- 高风险业务规则有自动化测试。
- 手工验收问题已修复或记录为已知限制。
- 发布清单无阻塞项。

## P8：发布交付

目标：交付可安装、可恢复、可说明的版本。

产物建议放置：

```text
docs/release/
  v0.1.0-release-notes.md
  known-issues.md
  build-instructions.md
```

必须包含：

- 版本号。
- 构建产物。
- 发布说明。
- 已知问题。
- 备份恢复说明。
- 回滚或重新安装建议。

通过标准：

- Android 安装包可安装运行。
- 新安装环境主路径可用。
- 备份恢复通过验证。
- 用户知道这一版能做什么、不能做什么。

## P9：复盘与下一轮

目标：把实际使用反馈转成下一轮需求。

产物：

- 复盘记录。
- 用户反馈列表。
- 缺陷列表。
- 下一版候选需求。
- 决策记录。

通过标准：

- 下一轮工作能从明确问题开始。
- 没有把临时反馈直接变成无边界开发。

## 阶段门禁表

| 阶段 | 进入条件 | 输出产物 | 退出条件 |
| --- | --- | --- | --- |
| P0 需求输入 | 有用户问题或想法 | 原始记录、待确认问题 | 核心问题可复述 |
| P1 需求设计 | P0 清楚 | 产品范围、规则、旅程 | 第一版范围稳定 |
| P2 产品规格 | P1 通过 | PRD、验收标准 | 可开发、可测试 |
| P3 交互流程 | P2 通过 | IA、流程、页面清单 | 主路径无断点 |
| P4 UI 设计 | P3 通过 | 高保真 HTML 原型、UI 规范、页面规格 | 用户确认样式和流程 |
| P5 技术设计 | P4 通过 | 架构、领域、路线图 | 切片和测试明确 |
| P6 开发实现 | P5 通过 | 代码、测试、迁移 | 切片可运行 |
| P7 测试验收 | P6 完成 | 测试报告、问题清单 | 无阻塞缺陷 |
| P8 发布交付 | P7 通过 | 安装包、发布说明 | 用户可安装使用 |
| P9 复盘 | P8 发布 | 反馈、下一轮计划 | 新一轮输入明确 |

## 需求到验收的追踪

每个功能都应形成追踪链：

```text
用户问题 -> 需求条目 -> 用户旅程 -> 页面/交互 -> 可视化 UI -> UI 规格 -> 技术切片 -> 测试用例 -> 验收结果
```

如果某个开发任务找不到上游需求或下游验收标准，agent 应先补齐规格，而不是直接写代码。

## AI agent 在各阶段的职责

- 需求阶段：整理、拆解、识别冲突和待确认问题。
- 产品阶段：写 PRD、验收标准、字段状态说明。
- 交互阶段：设计流程、页面清单、异常路径。
- UI 阶段：产出高保真可交互 HTML 原型、视觉系统、页面规格和组件状态。
- 技术阶段：设计架构、数据模型、服务边界和测试策略。
- 开发阶段：实现切片、写测试、更新文档。
- 测试阶段：执行自动化和手工验收，输出缺陷。
- 发布阶段：生成构建说明、发布说明和已知问题。

agent 必须先判断当前任务属于哪个阶段，再选择对应产物和验证方式。
